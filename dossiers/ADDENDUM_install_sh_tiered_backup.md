# ADDENDUM — `install.sh` TIERED STATE BACKUP
**Parent:** RocknixNightlyMigrationDossier.md (§13 supersedes — see note)
**Audience:** Claude Code (deep-dev implementer)
**Provenance:** ETK prototyped by Gemini + operator; moved into Claude for professionalization; deep dev now in Claude Code.

---

## §A. WHY (context the diff must respect)

The operator's dev protocol is: **every ETK change is deployed via `install.sh`** — never a from-scratch card flash, OS moves forward via Rocknix's in-place updater. So `install.sh` *is* the repair/sync path under continuous test, and its vault sync (Steps 2/4) has been exercised heavily and is trusted.

The gap: `install.sh` safeguards **only the shader vault**. Telemetry ledgers, tuned per-game configs, and RPCS3 user save data have **no host backup**. Under in-place updates this is latent (storage persists), but a card death, corruption, or an update that forces a reflash (cf. dossier §7, `sm8250: install rocknix abl`) loses all of it.

This addendum widens the **already-trusted sync mechanism** to cover mutable-precious state. It is not a new subsystem — it is more coverage on the path the operator already runs every cycle.

---

## §B. THE TIER MODEL (locked)

The vault is safe to sync **bidirectionally** only because shaders are **immutable** — a banked `.bin` is content-fixed, so `--ignore-existing` in both directions can never regress anything. Ledgers, configs, and saves are **mutable**, so they need different semantics. Three tiers:

| Tier | Contents | Mutability | Sync policy |
|---|---|---|---|
| **A — Immutable vault** | `vault/$CHIPSET/<ID>/shaders/` | Append-only, content-fixed | **Unchanged.** Bidirectional `--ignore-existing` (current Steps 2 & 4). |
| **B — Mutable-precious** | telemetry ledgers, tuned configs, RPCS3 user profile (saves/trophies/licenses) | Live-mutated on rig | **Backup always** (rig→host, every run). **Restore gated** (host→rig, flag only). |
| **C — Large regenerable** | `dev_hdd0/game/<ID>` blobs, `.psn` launchers, the per-game mango-enable key | Regenerated by the TOOLS installer from the operator's `.pkg`/`.rap` | **Not synced.** Accept re-install on catastrophe (operator decision). |

**Core insight that makes B+C compose cleanly:** a reinstalled `.pkg` yields the **same title ID**, so a restored `custom_configs/config_<ID>.yml` from Tier B re-attaches to the regenerated Tier-C game blob automatically. Configs survive via ID even though the blob is thrown away and rebuilt. This is why tuned configs are Tier B and game blobs are Tier C — they recover independently and re-converge on ID.

### B.1 Savedata reclassification (the one correction to the operator's first instinct)
The operator's "accept re-install for games" decision is correct **for blobs**, but RPCS3 **save data is not regenerated by a `.pkg` re-install** — it's irreplaceable gameplay, small, and mutable. It moves out of Tier C into **Tier B**. `uninstall.sh` already treats savedata as sacred ("keeps your save data"); a card death must not be the one event that doesn't.

Implement Tier-B RPCS3 coverage as the **whole user-profile tree** rather than cherry-picking `savedata/`:
- Back up `$RPCS3_DEV_HDD0/home/` as a unit. It subsumes `savedata/`, `trophy/`, and `exdata/` (the `.rap` licenses) in one rule. All small relative to game blobs, all precious, no reason to split.

## §C. SYNC SEMANTICS (the part that's easy to get wrong)

**Backup (rig → host): runs on EVERY `install.sh`.**
- Direction: rig is authoritative, host is a dumb snapshot.
- rsync: plain mirror via `$RSYNC_CMD` (NO `--ignore-existing` — host must track edits to existing ledgers/configs).
- NO `--delete` — host snapshot is an archive; never prune it just because the rig dropped a game's config (mirrors the existing "host `./vault` never auto-deleted" philosophy).
- **Read-only on the rig → adds zero SD writes.** Stays within the Phase-5 treadwear discipline. This is why backup can be unconditional.

**Restore (host → rig): GATED behind `--restore-state`, fresh/reflashed rig only.**
- Must **OVERWRITE** rig-side state — do **NOT** use `--update` or `--ignore-existing`. A just-reinstalled game drops a *template* `config_<ID>.yml` whose mtime is **newer** than the tuned backup, so `--update` would skip the restore and silently leave the game on template tuning. Plain `$RSYNC_CMD` host→rig (overwrite) is required.
- NO `--delete` on restore either (fresh rig has nothing extra; `--delete` is pure downside risk).
- Document loudly in-script: restore is **destructive to rig-side live state** and is intended only when standing a fresh/reflashed rig back up. It must never be part of a routine update.

**Mirror the gating idiom from `uninstall.sh`'s `--zap-vault`:** default = safe (backup only), destructive direction = explicit flag. Parse the flag right after `source ./scripts/env.sh`; tolerate it in any arg position (don't hard-pin to `$1`).

## §D. EXACT PATHS (derive from env.sh — Immutable Law #2)

Reuse existing exports; **do not hardcode**. Existing in `scripts/env.sh`:
- `ETK_ROOT`, `CHIPSET`
- `TELEMETRY_DIR` (`$ETK_ROOT/etk_telemetry` — contains `sessions.tsv`, `config_changes.tsv`, `career/`, `pit_note.txt`)
- `RPCS3_CUSTOM_CONFIGS` (`…/bios/rpcs3/custom_configs`)
- `RPCS3_DEV_HDD0` (`…/bios/rpcs3/dev_hdd0`)

**Add to env.sh** (so both halves of the sync name it once):
```sh
# RPCS3 user-profile tree (saves, trophies, .rap licenses) — Tier-B precious,
# backed up by install.sh, restored only via --restore-state.
export RPCS3_HOME_DIR="$RPCS3_DEV_HDD0/home"
```

**Host-side snapshot root** — local to `install.sh`, mirroring how `./vault` is already a literal there. Define once near the pipeline controls:
```sh
HOST_STATE_DIR="./state"     # Tier-B host backup tree; never auto-deleted (cf. ./vault)
```
Suggested host layout under `$HOST_STATE_DIR/`: `etk_telemetry/`, `custom_configs/`, `rpcs3_home/`.

### D.1 Tier-B source set (rig side)
| Host dest (`$HOST_STATE_DIR/`) | Rig source (env var) |
|---|---|
| `etk_telemetry/` | `$TELEMETRY_DIR/` |
| `custom_configs/` | `$RPCS3_CUSTOM_CONFIGS/` |
| `rpcs3_home/` | `$RPCS3_HOME_DIR/` |

`RECENT_ID_FILE` (`…/etk/vault/last_played_id.txt`) is tiny mutable state living at vault root, **outside** the `vault/$CHIPSET/` scope that Step 2 currently pulls, so it is **not** backed up today. It self-regenerates on first game launch, so it's optional — fold it into Tier B only if trivial; otherwise note and skip.

## §E. INSERTION POINTS (don't disturb the trusted vault sync)

`install.sh` step order today: `0` probe/quiesce → `1` provision → `2` **VAULT PULL** → `3` deploy scripts → `4` **VAULT PUSH** → `5` pitstop iface → `6` sentry.

1. **Flag parse:** immediately after `source ./scripts/env.sh`. Set `RESTORE_STATE=0`; flip to `1` on `--restore-state`. Echo an intent banner (mirror `uninstall.sh`'s `--zap-vault` warning style).
2. **Tier-B BACKUP:** new sub-step appended to **Step 2** (the existing backup phase), *after* the vault pull. `mkdir -p` the three `$HOST_STATE_DIR/*` dests; plain-mirror each rig→host per §C. Skip-with-`[SKIP]`-message if a rig source dir is absent (fresh rig, first run).
3. **Tier-B RESTORE:** new conditional sub-step in **Step 4** (the existing push phase), `if [ "$RESTORE_STATE" = "1" ]`. Overwrite-push each host→rig per §C. Provision rig dest dirs first (`mkdir -p` over SSH; Step 1 already creates `$RPCS3_CUSTOM_CONFIGS`, add `$RPCS3_HOME_DIR` and `$TELEMETRY_DIR` to Step 1's provisioning list). On default runs this block is silent/no-op.
4. **Step 1 provisioning:** add `$TELEMETRY_DIR` and `$RPCS3_HOME_DIR` to the existing `mkdir -p` list so a restore target always exists.

Use the existing `$RSYNC_CMD` variable and the house `--exclude='.DS_Store'` pattern throughout. Match the existing `${C}/${G}/${Y}/${R}` echo banner style and the `[OK]/[SKIP]/[WARN]` vocabulary.

## §F. DO-NOT-TOUCH / DECISIONS LOCKED

- **`ROCKNIX_SYSTEM_CFG` (`/storage/.config/system/configs/system.cfg`) is NOT Tier B.** It is a **global, shared** Rocknix file holding settings for *every* emulator, not just PS3. Backing it up / restoring it wholesale would clobber non-PS3 settings on the rig. The per-game mango-enable key the installer writes here is **regenerated** by the TOOLS installer on each game re-install → it is effectively **Tier C**. Leave it alone. (If finer-grained per-key backup is ever wanted, that's a separate, careful task — not this one.)
- **Game blobs (`$RPCS3_GAME_DIR/<ID>`) stay Tier C.** Operator decision: re-install from `.pkg` is the accepted cost of a catastrophe. **Precondition (state it in-script as a comment):** the operator must keep `.pkg`/`.rap` originals in their off-device library, because the TOOLS installer deletes staged files from `$PKG_STAGING_DIR` on success.
- **`.psn` launchers stay Tier C** — regenerated by the installer on re-install.
- **Tier A vault sync (Steps 2/4 bidirectional `--ignore-existing`) is unchanged.** Do not refactor it while adding Tier B; keep the diff additive.
- **No new SD writes on default runs.** Backup is rig→host read-only; restore (the only rig-write) is flag-gated.

## §G. DEFERRED (out of scope — do NOT implement unless explicitly asked)

**Sentry self-snapshot on game exit.** A hook on the Sentry's `RUNNING→IDLE` edge could copy-if-changed Tier-B state into the vault tree so `install.sh`'s pull captures it automatically, shrinking the loss window from "since last `install.sh`" to "since last game exit." Tempting, but: (a) the operator runs `install.sh` frequently, so the window is already small; (b) it adds SD writes on every exit, which must respect Phase-5 treadwear (copy-if-changed + clean-exit gating only); (c) it touches the load-bearing Sentry state machine. **Leave for a separate dossier.** Note it in the backlog; don't fold it into this diff.

## §H. ACCEPTANCE CRITERIA

1. **Default run is non-destructive to rig state.** `./install.sh` with no flags backs up Tier B (rig→host) and writes **nothing** to rig-side telemetry/configs/home. Verify rig `sessions.tsv` byte-identical before/after a default run.
2. **Backup is incremental + additive.** Second consecutive default run transfers only changed/new Tier-B files; host snapshot is never pruned.
3. **Restore is overwrite + gated.** `./install.sh --restore-state` against a fresh rig that already has a template `config_<ID>.yml` results in the rig holding the **tuned** backup config (proves overwrite beat the newer template mtime — the `--update` trap).
4. **Restore is inert without the flag.** No host→rig state write occurs on any run lacking `--restore-state`.
5. **Treadwear:** a default run issues no writes under `/storage/games-internal/roms/etk/etk_telemetry`, `…/custom_configs`, or `$RPCS3_HOME_DIR` on the rig.
6. **Fresh-rig absence handled.** First-ever run (no rig Tier-B dirs yet) emits `[SKIP]`, exits 0, doesn't error.
7. **Tier A untouched.** Vault pull/push behavior and output are unchanged vs. pre-diff.
8. **No hardcoded paths.** All new paths resolve through env.sh exports (incl. the new `RPCS3_HOME_DIR`).

### Test plan
- **T1 (backup):** on the live rig, run default `install.sh`; diff `./state/` against rig Tier-B sources; confirm match, confirm rig unchanged.
- **T2 (idempotent backup):** run again; confirm near-zero transfer, host snapshot intact.
- **T3 (restore overwrite):** on a scratch/fresh rig, TOOLS-install one game (drops template config) → `./install.sh --restore-state` → confirm rig `config_<ID>.yml` == tuned backup, and `$RPCS3_HOME_DIR` saves restored.
- **T4 (gating):** default run after T3 edits a config on-rig; confirm host backup tracks the edit and no restore clobbers it.
- **T5 (savedata round-trip):** back up, wipe a save on rig, `--restore-state`, confirm save returns.

## §I. DOSSIER §13 RECONCILIATION

Parent dossier §13 framed the backup gap around a **from-scratch reflash** and prescribed manual `rsync` lines. Given the operator's **in-place-update + always-`install.sh`** protocol, that manual procedure is superseded by this addendum: Tier-B backup becomes automatic on every deploy, and the manual rsync block in §13 should be replaced by a pointer to `--restore-state`. When updating the parent, soften §13 from "you must remember to rsync" to "Tier-B state is captured automatically each `install.sh`; restore a reflashed rig with `./install.sh --restore-state`," and keep the §7 reflash caution as the scenario that makes the host snapshot matter.
